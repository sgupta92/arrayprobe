# Enhancements
> Corrections and new science, in a separate installable package the port never depends on.

**In short:** `arrayprobe` never depends on this package, and a test fails if that reverses. Every correction ships with its effect measured both ways on the same data, including the ones measured inert.

**Which engine?** Enhancements act on the UIOOPS v3.5 engine; an earlier translation of UIOOPS v3.1.4 reproduced archived products and is not part of this package. Four modules correct defects the UIOOPS developers fixed themselves in v3.5, where applying one would double-correct. Each module declares its engines, enforced at resolution time: [Which enhancements apply to which engine](23-enhancements-by-engine.md).

**When does one act?** Each module declares a `stage` (decode, image processing, size distribution and combine, or post-combine export); a `proc`-file correction has nothing to do until framing has run. The diode and inter-arrival tools, which are not corrections, declare one too: [Which enhancements act at which processing-chain stage](25-enhancements-by-stage.md).

**This page covers corrections against UIOOPS** (`arrayprobe-uiops-enhancements`, 36 modules). SODA-2, NCAR's IDL chain, has its own, `enhancements_soda2` (`arrayprobe-soda2-enhancements`) — 18 correction modules plus one diagnostics-only module, documented in `enhancements_soda2/README.md` and `enhancements_soda2/BACKLOG_STATUS.md`.

**See also** [Findings](07-findings.md) for what is being corrected · [Conventions](09-conventions.md) for why the split exists · [All-on sets, per probe and engine](41-all-on-sets.md) for what "every enhancement on" means for a given probe.

**In a notebook:** `examples/2_processing/09_enhancement_ab.ipynb` switches `outoffocus` on in an
`[enhancements]` table and runs it A/B on the tracked dense demo flight under both engines, down to
the size distribution.

An engine translates its original faithfully: there, a "fix" that changes output is a defect, except the default-on corrections to data-destroying defects listed in [Choosing an engine](27-choosing-an-engine.md#corrections-engine-35-applies-by-default).
Everything that changes output lives in `arrayprobe-uiops-enhancements`, which depends on `arrayprobe`
and never the reverse — enforced by an AST-based test and verified by uninstalling the package and
re-running the port's full suite.

```bash
python -m pip install arrayprobe-uiops-enhancements
```

Contributors working from a checkout of the repository install it in editable mode instead:
`.venv/Scripts/python.exe -m pip install -e enhancements_uiops` (Linux / macOS: `.venv/bin/python`).

Each module is opt-in, has its own design document, and reports its effect on real data,
including where it is **zero**: listing only confirmed problems would distort the picture.

## Speed work is the exception: it lives in both spaces

Performance is split not by where it came from but by **whether it moves a written byte**.

| The change | Where it lives |
|---|---|
| Byte-identical, opt-in, no new dependency | the **port** |
| Changes any output, needs a dependency the port refuses, or trades accuracy for time | **enhancements** |

So the parallel decode and flags (`--s2-jobs`, `--chunks`, `--jobs`) are in the **port**: their
output is byte-identical to the serial path, asserted on every channel selection and every
sidecar, and all three default to serial ([user guide](02-user-guide.md)). No module in this
package is a speed enhancement.

## Does it change *your* numbers?

A correct fix can have nothing to do on the configuration that produced the archived products.
Three modules (`wide_hollow_fix`, `spot_edge_fix`, `hole_edge_swap`) are **inert** there — the
modified reject thresholds skip the hollow block they correct — so their headline figures
are stock-configuration measurements. `enhancements_uiops/docs/applicability_matrix.md` states this per
module, measured on a real file.

An active module can still barely matter, because the first five size bins are unused.
`last_record_fix` recovers hundreds of particles per file, single digits of them in used bins;
`zero_image_recovery` recovers particles across the whole size range.

**A figure measured on a sparse file may not carry to a dense one; only running both tells.** `outoffocus` was measured in 2026 on a 49,637-particle file and again on
the densest held, **17,289,449 particles**, and the diameter-ratio and rate figures from that run
still stand. **The distribution-effect figure does not**: `outoffocus.py` applied Korolev's (2007)
correction in the wrong direction (it multiplied by `size_factor` where the paper divides), so the
**−6.1 % of used-bin particles** and "every one of the 22 affected bins loses particles and none
gains" result were both measured under that wrong-sign correction and are **superseded**
(`enhancements_uiops/docs/CORRECTIONS.md`, part `outoffocus.py`, section *The direction*). The
direction is fixed in code and covered by a regression test; no dense-file figure is quoted for
the corrected direction.

## Running them

`arrayprobe run --enhancements <config.toml> <raw...>` runs the engine the config names as
a subprocess, resolves the enhancement set the config names, applies the ones with a driver
adapter (12 of the 41, the keys of `pipeline._APPLIERS`) onto copies named
`<stem>.enh.<kind>.nc`, and writes a `<sd>.enhancements.json` sidecar recording, per module,
whether it resolved on, was applied, or was skipped and why. The port's own output is never
touched. Which enhancements apply on which engine:
[Enhancements by engine](23-enhancements-by-engine.md).

## How a correction is proved

Where the MATLAB computed something and mishandled it, there is a **real oracle**: the port's own
validated value, or the stock tree under Octave. `zero_image_recovery` is checked against stock MATLAB's own
particle framing; `outoffocus` re-derives the hollow diagnostics and must match the stored
columns bit-for-bit before its correction is applied; `overload_accounting_fix` reproduces the
port's `sum_IntArr` on unaffected seconds before touching the affected ones.

Where MATLAB never ran the code, no oracle can exist; the module says so and is validated structurally.

## Still open

A 2DC diode-size discrepancy between two source files is open: real 2DC data is held (a
1995 ACE-1 file, probe C1, 25 um), but the comparison that would settle it has not been made. The
per-particle classifier (`ml_accept_reject.py`) has a heuristic and a numpy baseline; the deep
model is not built, because the limit is a labelled set of ~21 particles.
