# Which enhancements change the archived production output — measured, 2026-08-29, re-audited 2026-09-10

An enhancement can be perfectly correct and still have nothing to do on the configuration that
made the archived products. Three of the correction modules are in exactly that position, for one
shared reason, and the 2026-08-29 audit showed that saying so only in some places misleads: a
"60.4 % of calls are spurious" headline reads as a live figure when the code path never executes.

So this table answers one question per module: **on a file processed the way the archived products
were processed (`ORACLES_PRODUCTION`, `rej_hollow = 0`, aspect ceilings 4), does this enhancement
change anything?** Measured on `base160906064403` (49,637 particles, 4,110 seconds) unless stated.

**Re-audited 2026-09-10 against the requirement** (*"the impact of the enhancements will need to be demonstrated
with impact on data"*). All 42 shipped modules have a row (`brown_francis_1995`, `intarr_policy`,
`reaccept_every_event_fix` and `published_dof` added 2026-09-14; `probe_crossover` added
2026-09-20, having shipped with no row — found by `test_community_value_current.py`, which is
the arrangement this table's own check exists for). Before the audit, ten rows carried no
number at all — seven new-capability modules whose entry read only "n/a — changes no computed
value", plus `particle_clustering`, and the two literature modules whose rows read "not yet
measured on real field-campaign data". **Eight of those ten now carry real measured numbers**, taken from
the tracked `proc`/`sd` fixtures and a real field-campaign TAS sidecar. The remaining two
(`spec_artefact_filter`, `particle_clustering`) state *precisely why* they cannot be measured from
what is held, rather than leaving a vague "not yet".

"Changes no computed value" is a true and important claim for a new-capability module, but it is
not the same as "has no demonstrated impact" — what those modules *add* has a magnitude, and the
audit measured it. Two of the results were genuinely surprising and are recorded as found:
`arco_export` makes a small file **larger**, and `effective_density` maps only a quarter of real
particles.

**This table is about a configuration, not about an engine.** It answers *does this enhancement change anything on a file processed the way the archived products were processed* — every row's first evidence column is measured on the earlier translation (v3.1.4). Which **engine** each enhancement may be applied to is a separate question with its own answer, declared in `arrayprobe_enhancements.applicability` and rendered at `docs/23-enhancements-by-engine.md` — that page is the *state* (applies / superseded / variant-only), so this table does not duplicate it.

**The fifth column, added (2026-09-14), is the *measured consequence* on the v3.5 demo reference** (`demo_flight_dense_raw.2DS`, decoded under engine 3.5, 240 particles / 40 with `part_z > 0`) — the number nothing printed before this stage. Eight modules have a driver adapter wired in `pipeline.py` and a real number here, sourced from `docs/measurements.json`'s `v35_<module>` keys, never typed by hand (`tools/v35_ab_summary.py`, `tests/test_community_value_current.py`'s
`test_the_v35_column_agrees_with_measurements_json`). The rest were not separately A/B'd against
v3.5 in this stage's ~45-minute time box; each says so rather than a fabricated number, and a
`SUPERSEDED`/`VARIANT_ONLY` cell names that state (checkable against `applicability.py`) rather than a magnitude, because the module does not run on v3.5 in the first place.

## The lesson this table exists to prevent

Every "inert" row is inert for the *same* reason — `rej_hollow = 0` skips
`calculate_reject_unified.m:278-369` entirely — and each was discovered separately, at different
times, after its headline figure had already been written down. A figure measured under the stock
configuration is a fact about stock, not about the products; when the two configurations differ,
the row must say which one it measured.

None of this makes the inert modules wrong or worthless: they are correct fixes for real defects,
they matter for anyone running UIOOPS with `rej_hollow = 1` (its own default), and the unapplied Korolev size correction turns three
of them live by re-deriving the block. They just do not change the archived products' numbers.
